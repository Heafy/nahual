Computer Vision · Hand Detection

Before anything gets classified, the system has to see a hand.

→

MediaPipe's HandLandmarker does the detection. The exact same settings run when collecting training data and when recognizing live, so the model never sees a different kind of input.

Before we go further, this is where the AI part begins. Computer vision is the branch of AI that teaches a computer how to understand images and video, turning pixels into structured information, in this case, where a hand is and how it's posed.

And for that I'm using Google MediaPipe, an open source framework. It works for image classification, face detection, full human body poses, but I'm using it for detecting hand landmarks in an image. It takes in a continuous stream of video and outputs the hand landmarks and coordinates. As you can see, when we run it, it gives 21 hand landmark points per hand, in a 3D environment, per frame.

Detection quality is tuned deliberately (tracking confidence), and the exact same settings are used both when collecting training data and when recognizing live, so the model is never surprised by a different kind of input.

This is the foundation everything downstream depends on.

Machine Learning · Decision Trees

Before the forest, a single tree: one yes/no question at a time, until it lands on a letter.

  • Root and internal nodes each ask a yes/no question about the hand
  • Every answer narrows down which letters are still possible
  • A leaf node is the final answer

Built during training: thousands of possible questions tried, keeping whichever split separates the letters best. But a single tree only memorizes. Show it 200 photos of one hand, and it fails on someone else's.

A decision tree is a supervised learning algorithm used for classification and regression tasks, made of a root node, branches, and leaf nodes.

It splits the dataset based on feature values, creating pure subsets where every item belongs to the same class, by asking different questions. For example: the root node asks, is the index fingertip higher than this line? Yes passes to an internal node, no goes to a different question. That internal node asks, is the thumb touching the middle finger? Yes, it's letter B.

The tree builds itself during training. Every question tries thousands of possibilities and keeps whichever one best separates the letters still in play, until it ends on a single answer. It's the same kind of rule you'd use to describe a hand sign yourself: thumb up, index and middle extended, fingers together. A tree learns the same kind of rule, just measured instead of described.

But a single tree only memorizes. Give it 200 photos and it learns your hand, then fails on someone else's. The fix, next: many decision trees, each judging on a random slice of the data, a forest.

Machine Learning · Random Forest

Fix it with many trees, each judging on a random slice of the data.

  • Solid accuracy on a modest, hand-labeled dataset, no need for tens of thousands of examples per letter
  • Quick to retrain: add a few samples for a confused letter and the whole model rebuilds in seconds
  • A simpler choice than a neural network on purpose, trading a little peak accuracy for something fast to train and easy to inspect when two letters get confused

One tree memorizes. The fix is 200 decision trees, each one using only a random subset of the features to decide how it splits the data, on purpose. No tree ever sees the full picture, so the trees stay different from each other.

Each tree makes its own prediction based on what it learned from its part of the data, and the trees vote independently; the system averages their answers. That agreement is the confidence: if 190 out of 200 trees say "B", that's about 95% confidence, showing how much the trees agree. The confidence threshold is set at 65% agreement for static letters and 40% for the moving ones, since motion is harder to pin down frame by frame, so it gets more room.

Why Random Forest: it trains in seconds on a MacBook, no GPU, no cloud resources, and runs fast enough for live video with low device requirements. It's also inspectable, so when two letters get confused, I can see exactly which pair and why.

Challenges Along the Way

The smooth demo took real debugging to get there.

Challenge 1 · Dialing in detection

Problem MediaPipe's detection, presence, and tracking confidences all interact. Too loose, the hand flickers and false-fires; too strict, it never appears. Finding one setup stable across lighting and hand positions took real iteration.

Fix Locked the balanced configuration into a single shared config, so every tool sees the exact same detection.

Challenge 2 · Lost hands in motion

Problem Even with detection stable, fast motion still dropped the hand mid-gesture, exactly when the dynamic letters need it most.

Fix Raised tracking sensitivity, interpolated the remaining gaps, then retrained the dynamic classifier on the cleaner motion data.

9 → 3 dropped frames per quick gesture

Challenge 3 · Worse on the web

Problem Hosted, the demo felt worse than local. Latency starved the model of frames and eroded confidence below its threshold.

Fix Instead of patching the network, moved recognition fully into the browser. No round trip per frame, and it predicts bit-identical to the desktop app.

Two problems in the hand detection itself, one in how it was served. Sometimes you tune the settings, sometimes you rethink the whole architecture.

Getting here was not a straight line.

Challenge one was just getting MediaPipe to see the hand reliably. Its detection, presence, and tracking confidences all interact, and there was no obvious right combination: too loose and the hand flickers and false-fires, too strict and it drops out. It took real iteration to find one setup stable across lighting and hand positions, and I locked that into a single shared config so every tool sees the exact same detection.

Challenge two is closely related, still the hand detection: even with detection stable, fast motion still dropped the hand mid-gesture, exactly where the dynamic letters live. Tuning tracking sensitivity cut dropped frames during a quick gesture from about nine down to about three, and I filled the remaining gaps with interpolation. Because that changed the motion data, I retrained the dynamic classifier on the cleaner sequences.

Challenge three was a different kind of problem. The web demo felt worse hosted than it did locally. It turned out to be network latency starving the model of frames and quietly eroding its confidence below the threshold, not a compute problem. Throttling and batching helped, but the real fix was architectural: move recognition fully into the browser, so there is no network round trip per frame. I verified it predicts bit-identical to the desktop app.

The point: real problems, reasoned through. Sometimes you tune the settings, sometimes you rethink the whole architecture.

Current Limitations and Roadmap

Honest about where it is today, and where it goes next.

Today · Where it stands

  • Recognizes individual letters (fingerspelling), not full words, phrases, or continuous signing yet.
  • Trained on data from a single signer so far.

Next · The roadmap

  • Broaden the dataset across many more signers.
  • Validate accuracy with native LSM signers and the Deaf community.
  • Move from letters toward complete words and full-body gestures.

The biggest gains now come from more signers and more data, not more code.

A quick, honest word on scope before the ask.

Today, Nahual recognizes individual letters, fingerspelling, not full words, phrases, or continuous natural signing yet. And the dataset so far comes from a single signer.

The roadmap from here: broaden the dataset across many more signers, validate accuracy with native LSM signers and members of the Deaf community, and over time move from single letters toward complete words and full-body gestures, not just the hand.

The honest takeaway: the biggest gains now come from more signers and more data, not more code. Which is exactly what I am about to ask for.

Q&A

What would you like to know?

Your questions first. A few I hear often are queued up too.

  • 1

    Could this work for other sign languages, like ASL?

    The pipeline generalizes. Only the labels and training data are LSM-specific, so ASL needs its own dataset and a retrain, not a rewrite.

  • 2

    Is my camera feed private?

    Yes. MediaPipe and both classifiers run in your browser. No video and no landmarks ever leave your device.

  • 3

    Why Random Forest instead of a neural network?

    Strong accuracy on a small dataset, no GPU, and quick to retrain as data grows. A neural network would want far more data than collected so far.

  • 4

    Is it overfitted to your hand?

    A fair worry. Closed testing with several different users still recognized the gestures across different hand sizes and shapes.

  • 5

    What happens if the hand is lost mid-gesture?

    A short grace period tolerates a few missing frames, and any gap gets interpolated, so a brief dropout does not kill recognition.
